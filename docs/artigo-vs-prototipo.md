# Artigo × protótipo

O artigo já foi enviado e não pode mudar. Esta tabela lista o que o protótipo faz de diferente (ou ainda não faz). **Quem for apresentar precisa saber explicar cada linha.** Atualize sempre que o código divergir.

| Item | O que o artigo diz | O que o protótipo faz | Situação / como explicar |
|---|---|---|---|
| Modelo de linguagem | Família GPT (OpenAI) via API | gpt-oss via Ollama Cloud | Divergência. Argumento: custo e ausência de máquina local para rodar modelo aberto. Verificar se a justificativa convence |
| RAG | Base de conhecimento da equipe alimenta o modelo | Busca por chave (identificador do exame) na base, sem busca vetorial | Compatível: recupera conhecimento e injeta no prompt. Com poucos exames não há ganho em busca vetorial; entra se a base crescer |
| Classificação | Regras determinísticas | Regras determinísticas | Igual ao artigo |
| Leitura do PDF digital | pdf-parse | pdf-parse v2 (por cima do pdf.js da Mozilla), com a normalização Unicode desligada para preservar caracteres como o `µ` | Igual ao artigo |
| PDF protegido por senha | Não descrito | Proposta (BWL-02 já distingue "sem senha" de "senha incorreta"): o sistema pede a senha com mensagem fixa, sem o modelo; a senha só abre o arquivo e não é guardada | Extensão do protótipo. A senha nunca vai ao modelo, coerente com a pseudonimização. Rota e tela dependem do grupo |
| OCR | Tesseract.js | P1: pode não estar pronto | Se não ficar pronto, é afirmação sem sustentação no protótipo: apresentar como previsto |
| Camada de segurança | Aviso, especialidade conferida com a base, termos de diagnóstico/prescrição | Igual; acrescenta veredito (ex.: "preocupante") à lista de termos | Igual ao artigo, com lista ampliada |
| Pseudonimização | Dados enviados ao modelo pseudonimizados | O modelo recebe só dados estruturados, sem identificadores | Igual, e mais restritivo (nem texto bruto vai ao modelo) |
| Momento da explicação | Figura 3: após enviar a foto, aparece o cartão (analito, valor, barra colorida) e, logo abaixo, a explicação, sem clique. Figura 2: o paciente anexa a foto do exame dentro do chat | Sob demanda: o resultado (valor, faixa, cor, alerta) aparece sem IA; a explicação só é gerada quando o paciente clica em "Explicar com IA" num exame; o envio do laudo é uma porta própria (`POST /api/laudos`), não uma mensagem do chat | Divergência de interface, não de método: mesma explicação, mesma ordem, mesma segurança. Argumento: o botão poupa chamadas ao modelo e o alerta crítico nunca espera a IA |
| Estruturação por analito | Texto organizado por analito: nome, valor, unidade e faixa de referência do laudo; baixa confiança → novo envio | Parser por regras (`estruturarAnalitos`, BWL-03), sem IA, com confiança por analito e lista de linhas não interpretadas. Lê o formato do exemplo do artigo (Tabela 1: várias categorias de faixa; usa a "Normal", como na Tabela 2) | Igual ao artigo. Limite: cobre os layouts testados (tabela e blocos "Resultado:"); o próprio artigo cita como limitação "verificar o funcionamento com laudos de diferentes laboratórios" |
| IA como extratora de reserva | Não descrito | Não implementado | Trabalho futuro (não afirmar que existe): para layouts desconhecidos, o modelo extrairia os campos de um texto pseudonimizado e o código conferiria que cada valor, unidade e faixa aparece literalmente no laudo antes de aceitar. A classificação continuaria por regra |
| Cores na tela | Figura 3: barra com as faixas do PRÓPRIO laudo: verde = faixa normal, amarelo = faixa alterada, vermelho = "faixa mais elevada" (ex.: Diabetes ≥ 126) | Contrato §5.1: verde = dentro; amarelo = acima/abaixo sem alerta; vermelho = alerta crítico por limite configurado (com fonte), não pela faixa do laudo | Divergência. A barra por categoria exigiria levar `outras_faixas` (já extraídas na BWL-03) até o front. Explicar que o vermelho do protótipo é mais conservador: só aparece com limite crítico citável |
| Consentimento | "O tratamento dos exames depende de consentimento específico do usuário" | Não previsto no contrato nem nas tarefas | **[A CONFIRMAR no grupo]** Se não houver tela de consentimento, é afirmação sem sustentação no protótipo: apresentar como requisito da plataforma completa |
| Chat | Não descrito | Chat por exame: a 1ª mensagem é a explicação; depois o paciente digita dúvidas | Extensão do protótipo. Cada resposta passa pela mesma camada de segurança; apresentar como acréscimo, não como algo descrito no artigo |
| Base de conhecimento | Base mantida pela equipe | Fichas com texto baseado em fontes brasileiras (Ministério da Saúde/BVS, secretarias e hemocentro estaduais, SBD, SBEM) e especialidade escolhida pelo grupo | Compatível. A fonte de cada ficha está registrada; o texto não foi revisado por profissional de saúde (trabalho futuro) |
| Lembretes | Descritos | P2: só se sobrar tempo | Se não ficar pronto, apresentar como previsto |
| Execução | Não descrito | Docker | Detalhe de implementação |
| Avaliação com usuários | Não houve (trabalho futuro: legibilidade, revisão por profissionais, usabilidade) | Não houve | Não afirmar que o texto foi validado por profissionais de saúde |
